## Configuration and mapping

- Reusable `config/search.example.yaml` declares `linkedin.enabled: false` and `linkedin.limit: 5`. Private `config/search.yaml` can opt in. Bun is needed only when this source is invoked; it was unavailable on this host, so no live LinkedIn call or Bun CLI smoke test ran.
- Unique nonempty `DiscoveryPreferences.roleFamilies` become up to five bounded search queries, each with an explicit project location or `Germany` fallback and page 1. `linkedin.limit` caps accepted result jobs and detail requests, not the number of role queries: an empty first search may be followed by another role, and queries stop as soon as the result cap is filled. Empty roles make no call. A configured Germany-wide location remains `Germany`.
- Remote/hybrid/onsite (including `on-site`) map to the upstream workplace filter; `any` and unsupported values omit it. An explicit filter may be preserved as `workModel`; `employmentType` is never mapped to work model.
- A positive `postingAgeDays` up to 30 uses the next equal-or-wider upstream 1/7/14/30-day window; larger or absent ages omit upstream recency. The parseable search-card date becomes `postedAt` for authoritative project filtering. Missing or invalid dates are never invented.
- Validated numeric LinkedIn IDs become `externalId: linkedin:<id>` and canonical `https://www.linkedin.com/jobs/view/<id>` URLs. The detail company/title/location falls back to the search card. Description comes only from factual detail and is marked `SUBSTANTIVE` under the existing 80-character/title distinction; a card without detail remains `INSUFFICIENT`. `sourceName` is `LinkedIn`, `discoveredVia` is `LinkedIn public jobs`, and `ats` remains absent. Apply URL, seniority, industry, and job function are not added to canonical state.
- Existing ingest owns permanent IDs, external-ID and company/title/location deduplication, canonical source, and source ownership. A LinkedIn rediscovery or matching official ATS result converges on the same permanent ID in offline tests.

## Failure and personal-use boundary

- A failed search is an isolated LinkedIn source failure in `runDiscovery()`. A failed detail leaves a safe search card in Review as `INSUFFICIENT` and does not discard usable siblings. The default runner reports missing Bun clearly; it never invokes a fallback scraper.
- Public unauthenticated `jobs-guest` access is best effort, low-volume personal use and subject to LinkedIn Terms of Service and rate limits. No account login, cookies, session import, browser profile, CAPTCHA bypass, proxy rotation, fingerprint spoofing, credential storage, private API, JobSpy, or Apify was added.
- LinkedIn creates no cache database, tracker, history file, or other operational state. SQLite remains canonical. No real production DB, profile/CV, job folder, or generated artifact was modified. No Career Ops vendor file or pin changed; the pin remains `de7f7fe8fe65852b9743bbdce94f0304101a749e` (`career-ops-v1.34.0`).
