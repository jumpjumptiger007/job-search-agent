# Workflows

Discovery can be run manually from the dashboard, with `npm run discover`, or by a user-managed scheduler. Codex or Claude Code may also invoke these commands as external operator tools, but the application does not depend on either of them at runtime.

Configure ordinary private preferences in `config/preferences.yaml`; configure only the enabled bounded discovery routes in `config/search.yaml`. Known Greenhouse/Lever boards and explicit Personio career sources remain optional advanced sources. LinkedIn is disabled by default; `linkedin.enabled: true` with `linkedin.limit` opts into a low-volume, best-effort public unauthenticated source and requires Bun at invocation time. Its output passes through the same preferences and SQLite ingest path. Discovery performs provider discovery, filtering, normalization, canonicalization/deduplication, and ingestion, then stops at Review; it does not automatically score jobs. A person chooses Interested or Skip.

Codex Desktop is the external evaluation and tailoring-planning orchestrator. It uses read-only Career Ops evaluation, writing, and Germany/DACH policy, while SQLite remains the only canonical operational state. The validated project-owned `JobAnalysis` is stored in `jobs.analysis_json`; its 1–5 evaluation score is authoritative, while legacy `jobs.score` remains compatibility-only until later UI migration.

Candidate setup is intentionally private. Candidate claims are allowed only through validated references to the factual project profile. A validated analysis/tailoring plan is required before deliberate human-controlled material generation. The project deterministically writes `resume/rendercv.yaml` from selected profile facts; pinned RenderCV v2.8 renders and validates `resume/resume.pdf` before materials become `READY`. These are generated artifacts; SQLite owns operational state, and job folders contain generated/user application artifacts rather than SQLite mirrors. Cover-letter PDF/DOCX and package PDF remain on the existing compatibility path. The Next.js application has no runtime LLM dependency.

Temporary test or acceptance data created by Codex or automation must be cleaned up after validation. Cleanup may delete only artifacts created by that specific test run; never delete real user profile/CV files, historical job data, production-generated materials, or other user-owned runtime data unless explicitly instructed. Keep all private/runtime data git-ignored and out of commits.

Human approval does not apply for a job. A person must explicitly set application tracking states, and the tool must never auto-submit an application.
